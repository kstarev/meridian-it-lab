# AAC-007: Dry-run by default, a blast-radius limit, a break-glass allowlist, no stale plans

**Date:** 2026-11-14 · **Status:** Accepted; built, with the open checks listed in [MILESTONES.md](../../MILESTONES.md).

**Context:** A tool that removes access across a whole company can do a lot of damage quickly: a bad HRIS export can make everyone look like a leaver, and removing the last admin account locks IT out. Review alone isn't enough if a reviewer approves a huge plan without reading it. Each rail below is enforced by code or GitHub settings, not by the model or by care.

**Decision:**

- **Dry run by default.** Apply prints and records what it would do unless the repository variable `ACCESS_APPLY_MODE` is `mock-live`, and then it changes only the mocks. There is no mode for real systems.
- **Blast-radius limit, counted per cause-day, with a split plan.** Every removal or suspension is caused by one day's HR event (its `cause_date`). A day's bucket is over the limit when **5 or more people** (`blast_radius_people`) lose access because of that day, **or** **50 or more** accesses (`blast_radius_removals`) are removed or suspended on it. Removals with no HR event day form one extra "no date" bucket, checked against the same two numbers. There is no plan-total limit. The plan is **split**: over-limit buckets go to a separate **held plan** (its own pull request, bot branch `access/plan-held`) that needs **two** code-owner approvals; every other bucket stays in the **main plan**, which needs **one**. One bad day never blocks the rest. Every bulk import is held too, whatever its size (a bulk HR error gives one block finding and no removals for those people), and goes to the held plan. Why two numbers: on the tuning data the largest ordinary day removed many accesses from few people while the bulk import touched many people (see the [blast-radius report](../../../docs/evals/2026-11-15-access-blast-radius.md)), so counting accesses alone cannot separate them; people per day can, and 50 on one day catches a few people with very many accesses. Both are set in `access/policy/settings.yaml`, so changing them is itself a reviewed change. A required check counts approvals from code owners on the current plan and fails until there are enough. Apply checks the count again before it changes anything and applies a plan file only as its own part (`main` or `held`). The merge check recomputes the requirement from the plan file, so apply's rebuild (it splits a fresh plan and refuses a plan whose changes, `cause_date` included, differ from the same part) is what makes edited fields harmless.
- **Break-glass allowlist.** Accounts in `access/policy/break_glass.yaml` are never changed, by any plan. If a plan would touch one, that change is dropped and reported as a warning. A test proves no code path changes them.
- **No stale plans.** `plan.json` records the hash of the actual state it was built from. Before applying, apply collects the state again; if the hash differs, it stops and the next plan is built from fresh data.
- **Idempotent apply.** Each change is checked against the current state before it's made, so applying the same plan twice changes nothing the second time. Retries after a `429` or `5xx` are safe.
- **Suspend before remove,** where the API allows it, for leavers and people on leave; removal follows in a later plan.
- **AI suggestions never act on their own** ([AAC-006](006-model-choice-and-spend-cap.md)): a change that rests on an AI match or title mapping can't be in a plan until a person has approved that map entry.
- **Read and write are separate tokens.** Collectors hold read-only tokens; only apply holds write tokens, and only in the apply workflow.

**Consequences:**

- The planted mass termination is caught by design, and the results page shows it.
- Applying either part of the split plan makes the other stale: both were built from the same actual-state hash, so after one is applied the other is refused as "stale", rebuilt and approved again. The apply command line refuses the held part (it takes the approval count from the caller); the held plan is applied only when its pull request is merged with two code-owner approvals, which needs the owner's GitHub App and is not built.
- The owner is the only code owner, so a held plan pull request stays blocked by design. There is no override and no stand-in second approver anywhere; the blocked bulk-import pull request is the demo that the rail works.
- The limit was revisited on 2026-11-15 with the [blast-radius report](../../../docs/evals/2026-11-15-access-blast-radius.md): N = 25 per plan was replaced by a per-cause-day limit (5 people or 50 accesses) and the split plan. They are policy settings, not code. Behaviour changes compared with N = 25: a same-day non-bulk batch of 5 or more people is no longer held by the diff but goes to the held plan and is applied after two approvals; a plan of many days with 26 or more removals in total needs one approval when no single day is over the limit; and the main plan no longer waits for the held plan.
- Dry run by default means the demo shows plans and what apply would do; switching to `mock-live` is one variable.
