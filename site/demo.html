Simulated Slack, fake data

One request, from message to closed ticket

One fake employee asks Tier0 how to get onto the office Wi-Fi. Each step below shows what happened, with a short note on what code decided and what the AI model only suggested.

This is not a real Slack workspace. The conversation is a replay of one run of Tier0 on the lab's mocks of Slack, the staff directory and the ticket system. Every message, label and ticket note below comes from that run; none of it was written for this page. On the lab's clock, the message arrives on Mon 2 Nov 2026, 09:00 UTC.

The replay

What happened, step by step

  1. 01

    A person asks in Slack

    The employee

    Direct message with tier0Simulated Slack, fake data

    AS

    Anika Sato09:00

    I'm working from the Toronto office for the first time today, how do I get my work laptop onto the staff Wi-Fi

    The message is template T035 of the tuning month (tuning_month), word for word. Tuning data is what the project builds and tunes on; no sealed test set appears on this page.

    The sender, Anika Sato, is a fake person from the lab's fake directory. Tier0 gets the message as a Slack event, in a direct message.

  2. 02

    Code checks who sent it

    Code decided

    Checks before any model call

    Slack signature
    valid
    Sender matches an active directory account
    yes
    Kill switch
    off
    Rate limit
    allowed

    Code checks that the event really came from Slack and that the Slack user is an active account in the company directory. The sender's name is taken from the directory, not from the message.

    The kill switch is off and the sender is under the rate limit, so tier0 may act. No AI model has seen the message yet.

  3. 03

    Triage labels the request

    Model suggested, code decided

    Triage and the policy table

    Label the model gave
    other
    Policy tier
    A
    Policy action
    escalate

    The model picks one label from a fixed list. Here it said other: not a username question and not about someone else.

    Code looks the label up in a fixed table. For this label the table says escalate: hand it to a person, unless an approved guide answers it.

    On this page the model is the repo's offline stub (tier0.stub/tier0-stub-1), a keyword stand-in for Claude Haiku. It costs nothing and gives the same answer every time.

  4. 04

    A guide is picked, and code checks it

    Model suggested, code decided

    Guide picker and posting gate

    Request type the model gave
    how_to
    Guide the model named
    KB-001
    Message screen (code only)
    nothing found
    KB-001 approved by a person
    yes
    KB-001 flagged by the guide screen
    no
    Outcome
    post the guide

    The model sees only each guide's id, title and summary, never its steps. It names one guide, KB-001 (Connect to the office Wi-Fi), or none.

    Code decides whether to post it: the message screen found nothing that needs a person, and the guide is approved by a person and not flagged. Any no would have sent the request to a person instead.

    On this page no AI model made the pick: a scripted stand-in (stub/scripted) names the guide from the tuning month's answer key. In the lab the picker is Claude Sonnet 5.5, and it is off unless an option turns it on.

  5. 05

    Code posts the reply

    Code decided

    Direct message with tier0Simulated Slack, fake data

    T0

    tier0APP09:00

    Hi Anika, I'm tier0, Meridian's AI assistant for IT requests.

    Here's our guide for that:
    Connect to the office Wi-Fi
    1. Open your Wi-Fi settings and choose the network Meridian-Staff.
    2. When asked to sign in, use your work email address and your normal work sign-in.
    3. Accept the certificate named meridian-radius if your device asks about it.
    4. If the network does not appear, turn Wi-Fi off and on again and move closer to the centre of the floor.
    5. Still stuck after two tries? Post in #it-help and say which office and floor you are on.
    https://memory.meridian.example/runbooks/office-wifi.md

    Before and after sending

    Reply guard
    passed
    Access tokens asked for
    none
    Tool calls on an account
    none

    Code wrote every word of this reply. The greeting uses the first name from the directory. The first message says that tier0 is an AI assistant. The header comes from a fixed template, and the steps are the approved guide's, word for word, with its link.

    The reply guard checked the message before it was sent. Tier0 asked for no access token and called no tool, because a guide reads no account.

  6. 06

    The ticket records what happened

    Code decided

    Ticket IT-1 · queue service-desk · Awaiting reply

    1. tier0: triaged as other; policy: Tier A, action escalate.
    2. tier0: guide picker KS5: request type how_to, guide KB-001; message screen none.
    3. tier0: answered with the approved guide KB-001: its steps word for word and its link.

    Tier0 opens a ticket for every request and notes each step on it, so a person on the IT team can see what tier0 did and why.

    The ticket now waits for a reply: Awaiting reply.

  7. 07

    Three days later, code closes the ticket

    Code decided

    Direct message with tier0Simulated Slack, fake data

    Nobody replied, so after three days a scheduled sweep closes the ticket and tells the person how to reopen the question. The note is a fixed template, too. The ticket is now Done.

How this page is made: python -m tier0.site_demo --out site runs the ticket through the real agent in process, with no paid model and no network, and writes the run log and this page. A test fails if either drifts from a new run (the generator, ADR-036).
