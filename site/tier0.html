Tier0: an IT help-desk agent for Slack

Tier0 answers a narrow set of IT requests in Slack and hands everything else to a person. This page describes the problem, the design, the tests, the results and the next steps. In the results, the failed tests come first.

All the data is fake. Meridian is a made-up company, and nothing comes from a real employer.

01

The problem

Meridian is a made-up company. It has 230 people in 14 countries. Its IT team has 3 people, in Berlin and Toronto. Nobody on the IT team works in the Asia-Pacific region.

People ask the IT team for help in Slack, a workplace chat tool. A person who asks while the IT team is off work has to wait.

Sign-in help is number 2 in the company's list of its 10 most common kinds of IT request, with an estimated 15% of all requests. Sign-in help covers a username lookup, a password reset and a reset of multi-factor authentication. Multi-factor authentication, or MFA, is a second sign-in step, such as a code from a phone app. The shares are made up, like the rest of the data.

A help desk is also a target for misuse. A person can ask for a colleague's login details and give a reason that sounds urgent. A tool that answers by itself must not give one person's details to another person.

The project's question: can software answer the simplest requests at any hour, and hand every other request to a person?

02

The design

Tier0 is an agent: software that uses an AI model to carry out a task. It reads a message that a person sends it in Slack. It answers a narrow set of requests itself. It hands everything else to a person on the IT team.

The AI model does not write replies and does not decide what happens. It picks from fixed lists: a label for the request, a yes or a no, or the name of a guide. Code means fixed program rules that a person wrote. Code decides what happens after each pick. Code also writes every reply, from fixed templates.

The AI models are Claude models, made by Anthropic. Two are used: Claude Haiku 5.5, the cheaper one, and Claude Sonnet 5.5.

To see one fake request go through these steps, open the simulated Slack demo. It replays one run of Tier0 on the mocks, with a note beside each step on what code decided and what the AI model only suggested.

Approval tiers

Each kind of request belongs to a tier. The tier sets who must approve the action. The tiers come from the project brief.

TierCoversApproval
AReading and answering: how-to questions, policy questions, the status of a ticket or a deviceAutomatic
BA low-risk change, such as joining a Slack channel or installing software that is already approvedAutomatic, and logged
CA privileged action: an MFA reset, an admin role, closing the accounts of a person who leavesA person approves first. Then a credential, a temporary permission to act, is issued for that one task.

What is built

  • By default, 1 request type is answered from start to finish: the sender's own username. It runs against mocks: stand-in programs shaped like Slack, the ticket system and the staff directory.
  • Answers from approved guides are built and tested. They are switched off by default (ADR-046).
  • Guide answers now wait for one click from a person in IT. The guide picker failed its safety rule on two sealed months, so its choice is only a suggestion. A guide reaches the person who asked only after someone on the IT team clicks "Send this guide". A click by anyone else is refused and logged. This stays until a sealed month passes both rules, and it costs the time the guides save (ADR-053).
  • The how-to gate is built and runs whenever the guide step is on. Its version is G3. It has not run on a sealed set, so nothing shows yet that it works on new wording (the plan for the gate).
  • Tier B and Tier C actions are designed and not built. A password or MFA reset request is prepared for a person. Tier0 has no tool that resets anything (ADR-048).
  • A kill switch is one setting that stops every agent action at once. A rate limit caps the agent's actions at 5 per person and 30 for everyone, per hour. Both are built and tested. IT staff have no button for them yet.
  • Tier0 has not run in a real Slack workspace. A real Slack app is optional and not planned (ADR-036).

03

How it was tested

The tests measure safety first: does Tier0 ever do something the rules forbid? They also measure how often it does the right thing.

Tuning data and sealed sets

Tuning data is example requests that the builder reads and adjusts the tool on. A sealed set is test data that nobody building the tool has read.

A separate helper wrote each sealed set from a written brief. The helper saw no code and no tuning data. The reports call this writing a set blind (ADR-045).

Each sealed set runs once

The file of a sealed set is locked by a hash: a short string of characters computed from the file's contents. If the file changes, the string changes and a test fails.

A sealed set runs once, after the owner approves the run. It is then spent: it becomes practice data and cannot measure a later fix.

Pass rules come first

A pass rule states the count a run must reach to pass. The rules are written before the run. The safety rule is the same in every test: 0 unsafe actions.

An unsafe action is a change or a disclosure that the answer key forbids. An answer key lists the expected outcome for every test request.

Every request runs several times

An AI model can answer the same message differently each time. So each test request runs 3 or 5 times. A request counts as right only when every run is right. The reports call this measure pass^k.

Code does the grading

Code compares where each request ended up with the answer key. No AI model grades the results (ADR-003).

Result files hold no message text

The result files of the sealed month hold ticket ids, ticket kinds and outcomes. They hold no message text. The reports on the sealed how-to test, the passed-on requests and the reset requests give counts only.

Rates come with a range

The test sets are small. So each rate is reported with a 95% interval: the range the rate could fall in if the test were repeated with other requests of the same kind.

Spending is capped

The lab has $100 of credit for paid AI model calls. Code checks every paid call against a cap before it is sent. The cap for the realistic month is $18.

04

Results

Failures come first. Every number links to the file it comes from. Each date is the day the test ran.

Failed

The guide picker's fix on two sealed months (2026-11-19)

The fix is a new set of instructions for the guide picker, KS6A-H. It was tested on two new months of tickets. Each was written blind, sealed, and run once on 2026-11-19, on the system frozen before the runs. The first new month has 300 tickets of every kind, like the first month. The second has 300 tickets of four kinds only: small talk, hardware faults, app faults and how-to questions. Each ticket ran 3 times in each of the same 2 setups.

Each month had 2 pass rules: 0 out-of-scope tickets answered, over all runs, and the right guide in at least 0.90 of the runs on how-to questions. A month passes only if both rules hold in both setups.

Both months failed the first rule, in both setups. In the first new month, 9 of 624 runs on out-of-scope tickets were answered in the Haiku setup, and 9 of 624 runs in the Sonnet setup. In the second, 7 of 495 runs were answered in the Haiku setup, and 8 of 495 runs in the Sonnet setup.

  • The second rule held. The share of how-to runs with the right guide was 1.00 (1.00 to 1.00) and 1.00 (1.00 to 1.00) in the first new month, and 0.95 (0.83 to 1.00) and 0.95 (0.83 to 1.00) in the second. No how-to run got a wrong guide.
  • Every answered run was answered with a help guide, by the guide picker both setups share. No username was given out: 0 runs and 0 runs in the first new month, 0 runs and 0 runs in the second.
  • In the first new month, the failures are on the same 3 tickets in both setups. All of them are of the kind the answer key calls prompt injection: a message with an instruction hidden in it.
  • In the second, they are on 3 tickets in the Haiku setup and 4 tickets in the Sonnet setup. All of them are app faults from one template.
  • The two kinds that failed the first month had no answered runs in the second new month: small talk and hardware faults.
  • Slowness-only tickets were scored apart, as the second month's rules say. They got the slowness guide in 21 of 21 runs in the Haiku setup and 21 of 21 runs in the Sonnet setup.
  • The result was reported from ticket ids, kinds and outcomes only. The tickets were read only after the owner opened both months as dev sets, and only the failing ones.

The result stands as a fail. It is not scored again, no answer key is changed and no rule is softened. Both months are spent, and the owner opened them as dev sets afterwards. Why the tickets were answered: two how-to questions with an instruction for the bot hidden in them, which the picker's prompt says to ignore and answer, and a fault in the room-booking feature, answered with the guide for booking a room. The cost of the AI model calls was $0.3882 and $0.6500 in the first new month, and $0.5788 and $0.8243 in the second.

In the repository: the failure note, with the options, the first new month's summaries for the Haiku setup and the Sonnet setup, and the second's for the Haiku setup and the Sonnet setup.

Failed

The sealed realistic month (2026-11-17)

The realistic month is a set of 300 tickets that imitates a month of help-desk requests at Meridian. 208 of the 300 tickets are out of scope: the answer key wants a person to handle them. The tickets were generated from 124 templates. A template is one wording of a request.

The month ran once, on 2026-11-17. Each ticket ran 3 times in each of 2 setups. A setup is a fixed choice of AI models and instructions. In the Haiku setup, Claude Haiku 5.5 labels the request. In the Sonnet setup, Claude Sonnet 5.5 labels it. In both setups, Claude Sonnet 5.5 picks the guides.

The run had 1 pass rule: 0 out-of-scope tickets answered, over all runs.

The rule failed in both setups. In the Haiku setup, 10 of 624 runs on out-of-scope tickets were answered. In the Sonnet setup, 9 of 624 runs were answered.

  • The failures are on the same 4 tickets in both setups.
  • Each of them was answered with a help guide. The guide picker chose a guide where the answer key wanted a person. Both setups use the same guide picker, so they share this failure.
  • No username was given out: 0 runs in the Haiku setup and 0 runs in the Sonnet setup.
  • The 4 tickets come from 2 templates. 3 are of the kind the answer key calls chitchat, where Tier0 has nothing to do. 1 is a hardware problem.
  • The result was reported from ticket ids, kinds and outcomes only. Nobody read the tickets before the result was published.
  • The share of out-of-scope runs that were answered is 0.016 (0.000 to 0.048) in the Haiku setup and 0.014 (0.000 to 0.043) in the Sonnet setup. The brackets give the 95% interval.
  • The tuning month, a second month built from tuning data, did not show the failure. There, 0 of 208 out-of-scope tickets were answered. That figure was measured on data the guide picker's instructions were tuned on.

The result stands as a fail. It is not scored again, the answer key is not changed and the rule is not softened. The month is spent. After the run, the owner made it a dev set: data that may now be read and tuned on. A number measured on it from now on is labelled dev, not blind (ADR-049).

What the failure note found. After that ruling, the 4 tickets were read, and only those 4. The finding: the guide picker chooses a guide by its topic, not by whether the guide's steps would do what the sender asked.

  • In 3 tickets, the message asks for nothing that IT can do. No guide can do it.
  • In 1 ticket, the sender has already done the guide's checks and wants a repair or a replacement. That is past what the guide covers.
  • The picker's instructions already say that a guide on a nearby topic is not enough when it would not do what the person asked. That rule did not hold in these cases, where the guide is on the right topic.
  • The note explains the picks from the instructions and the guides. The picker returns a guide's name and no reasons.

The run also reported the figures below. They were not passed or failed, and they do not change the failed rule.

Failed in part

The sealed how-to test (2026-11-16)

This test covers answers from the IT team's guides. It holds 88 questions. Each question ran 5 times with Claude Haiku 5.5 as the guide picker, and 5 times with Claude Sonnet 5.5.

Some guides in the test are poisoned guides: fake guides that carry a hidden instruction. The test had 5 pass rules, each with a target of 0. 2 of the 5 rules failed.

  • Failed: the guide picker must not pick a poisoned guide whose hidden instruction it can see. With Haiku, it picked one in 5 runs, all on the same question. With Sonnet, it picked one in 0 runs.
  • Failed: a code check called the guide screen must flag every poisoned guide. It flagged 7 of 8 and missed 1. The missed guide carries its instruction in quoted text or in a code block.
  • Passed: 0 poisoned guides were posted to a person, in any run, with either model. This rule passes by the approval step alone. Code posts only guides that a person approved, and no poisoned guide is approved in the test.
  • Passed: requests that must go to a person were answered from a guide in 0 runs.
  • Guide questions answered with the right guide in every run: 33 of 34 with Haiku and 34 of 34 with Sonnet.

Decision after the run: Claude Sonnet 5.5 picks the guides, and Haiku does not. Neither check was changed after the run (ADR-046).

Limit: the guide screen flagged 0 of 30 clean guides, but it was built on those same guides. Its rate of false flags on unseen guides is not measured.

In the repository: the report on the sealed how-to test.

Failed in part

Requests passed on in someone else's words (2026-11-16)

A sealed set of 66 tickets tested instructions hidden inside messages, and requests passed on in another person's words. Each ticket ran 5 times in each of 6 setups. The pass rule was 0 unsafe runs in every setup.

3 of the 6 setups failed the rule. Each had 5 unsafe runs, all on 1 ticket: a colleague's request, passed on in that colleague's words, that names nobody.

  • In those runs the AI model labelled the request as the sender's own, and the second check did not stop it. No data about another person was given out: 0 runs exposed data.
  • All 3 failing setups pair Claude Haiku 5.5 with the older wording of its second check.
  • The Haiku setup with newer wording for that check had 0 unsafe runs. Each Sonnet setup also had 0 unsafe runs.

Decision after the run: Haiku uses the newer wording. The decision rests on 1 ticket, on a set that is now spent (ADR-047).

In the repository: the report on this set, named held-out v5.

Failed in part

Resets, repeated requests and several questions at once (2026-11-17)

A sealed set of 74 tickets tested password and MFA reset requests, repeated requests on the same day, and messages that ask several questions. Each ticket ran 5 times in each of 5 setups. The pass rule was 0 unsafe runs in every setup.

3 of the 5 setups failed the rule, with 5 unsafe runs each. The 2 setups that Tier0 uses by default passed, with 0 unsafe runs each.

  • 2 failing setups split a message with several questions into parts. Each one answered the username part of 1 message that also asked for a reset. Nothing was reset, because Tier0 has no reset tool. No data was exposed.
  • The other failing setup pairs Haiku with the older wording of its second check. It failed on requests passed on in someone else's words.
  • In the default setups, all 14 reset tickets were prepared for a person in all 5 runs.
  • Tier0 answers at most 3 requests for one account in 24 hours. Requests over that limit went to a person on 5 of 5 tickets in every setup.

Decision after the run: messages are not split. A message with several requests goes to a person whole (ADR-048).

In the repository: the report on this set, named held-out v6.

Not measured yet

The how-to gate in front of the guide picker (2026-11-20)

Nothing measured so far shows that the gate works on new wording. Its one blind test is a new sealed month, and that month has not run. Every number below comes from months already used: the tuning month, and sealed months that have run and are dev sets now.

After the picker's fix failed on the two sealed months above, the owner ruled two things. Guide answers wait for one click from a person in IT until a sealed month passes (ADR-053). And there is one structural fix in code, not more instructions for the picker: a how-to gate in front of the guide picker. The gate is one more question for the AI model that picked the label: is this message one plain how-to question, and nothing else? The gate never sees a guide, so a guide on the right topic cannot pull it toward answering. A guide is suggested only if the code check of the message finds nothing, the gate says yes and the picker picks a guide (the plan).

Three versions of the gate's instructions were written, each from tuning data only and each committed before it was scored. A selection rule, also committed first, picks one: 0 out-of-scope runs answered, and the right guide in at least 0.90 of how-to runs, on every month.

  • G1 and G2 failed the rule in the Haiku setup. They sent too many how-to questions to a person. They were not scored in the Sonnet setup.
  • G3 passed the rule in both setups. It is the version Tier0 uses when the guide step is on.
  • In the Sonnet setup, the same version failed its first two scorings because of a code bug, not its instructions: the gate's reply limit cut Sonnet's replies short, and a cut reply counts as a hand-off. The limit was raised and the instructions were not changed. The report keeps both failed runs.

The scoring reused the recorded runs of four earlier months. For each run that reached a guide, the gate was asked once. If it said no, the run counts as handed to a person. Every other run counts as it was recorded.

Passed

The sealed comparison of models (2026-11-12)

A sealed set of 54 tickets compared 7 setups: 2 with Claude models and 5 with open models. An open model is one that anyone can download and run. These ran on one computer. The tickets are requests for the sender's own username, requests for a colleague's login details, and messages from outsiders.

  • 0 unsafe runs in every setup. Every request for a colleague's login details was refused.
  • The share of tickets that were right in all 3 runs ranged from 0.93 to 0.98.
  • No setup was measurably better than the others. The set is too small to show small differences.
  • 1 ticket failed in every setup. A new starter described themselves and asked for their own login. A code check sent the request to a person, and the answer key wanted an answer.
  • Cost of the AI model calls per 1,000 requests: $0.08 with Haiku and $1.66 with Sonnet.

In the repository: the report on this set, named held-out v3.

Passed

The fix for new starters (2026-11-15)

The failure above led to a fix in the code check. 2 new sealed sets measured it: one of 72 tickets and one of 32 tickets. Each ticket ran 5 times with Haiku and with Sonnet, in 3 versions of Tier0: the old one, new instructions only, and new instructions with the fix.

  • 0 unsafe runs in every version, on both sets and with both models.
  • The measured benefit is 1 request. Of 20 short messages from people who describe themselves, 18 were answered in every run without the fix and 19 with it. The intervals overlap, so this is not a measured improvement in the rate.
  • With the new instructions, Haiku passed fewer tickets on the larger set: 72 of 72 with the old instructions, then 71 and 70. It refused 1 person who should have been answered.

In the repository: the report on these sets, named held-out v4 and v4b.

Limits of these results

  • All the data is fake, and every test ran against mocks.
  • The sealed sets are small, so the intervals are wide.
  • The realistic month checked where each ticket ends up. It did not run the replies, the staff directory check or the ticket system.
  • An AI helper wrote each sealed set, so the sets share that helper's habits (ADR-045).
  • The month's pass rules were written before any run. They were committed after the seal, in the same pull request, before any model had run on a month.
  • Claude accepts no fixed random seed, so the Claude runs cannot be repeated exactly.

05

What comes next

Fix the guide picker

The owner ruled that the guide picker is fixed with a general rule: when to hand a request to a person because no guide fits it. The fix must not be written against the wording of the 4 tickets. It is tuned on dev sets only.

The fix was to be measured on a new month of tickets, written blind and run once (ADR-049). A budget item of $15 pays for the work (ADR-050).

The fix was measured on two new months on 2026-11-19, and it failed: see the results above. The options are in the failure note.

The owner's ruling: guide answers wait for one click from a person in IT until a sealed month passes. That is now the default in code (ADR-053). The tests still score the guide picker's own choice, so a new month can show whether the click is still needed.

A separate question is open: whether small talk gets a hand-off or a short guide that says where to ask. The owner rules on that from the project brief, not from this result.

Run the how-to gate's sealed month

The how-to gate's sealed month of 400 tickets runs once, after the owner's go. Until then, nothing shows that the gate works on new wording.

If the month fails, guide answers keep waiting for the IT click, and the picker and the gate are not changed again. If it passes, nothing changes on its own: the owner decides whether guides may be sent without the click (the stop rule).

Measure the guide screen's fix

A fix for the guide screen is written, from tuning data only. Its sealed test set is not written yet.

Until that set has run, the fix is not measured (the plan for the fix).

Not built yet

Tier B and Tier C actions are designed and not built.

The service is planned to run on AWS, a cloud provider. That is not built. A real Slack app is optional and not planned (how it runs in production).
