Access-as-Code: access changes as a plan that a person reviews

Access-as-Code compares who should have access to an app with who does. It proposes the changes as a plan, and a person approves the plan before anything changes. This page describes the problem, the design, the tests, the results and the next steps. In the results, the failed test comes first.

All the data is fake. Meridian is a made-up company, and nothing comes from a real employer.

01

The problem

Meridian is a made-up company with 230 people and an IT team of 3 people.

The company uses about 140 apps. 45 of them sit behind single sign-on, or SSO: one company login that opens many apps. 95 do not.

Access means who can sign in to which app. The IT team cannot reliably say who has access to what across these apps.

A person's access should change when they join, when they move to another job and when they leave. These changes are handled from checklists. In the company's made-up list of IT requests, they are about 36% of all requests.

Access that should have ended can stay. The project brief gives an example: a person leaves, and their account in an app outside SSO stays open, because the checklist missed that app.

Evidence for audits is then put together by hand.

02

The design

Access-as-Code keeps the access rules in files: which job gets which apps. Code means fixed program rules that a person wrote. Code reads the rule files and the HR records, and works out what each person should have. Code also reads the account lists from the staff directory and from the apps, and works out what each person has.

The difference between the two is the plan: a list of proposed changes in plain English. The plan is a pull request: a proposed change that a person must approve before it takes effect. By design, the plan is updated every night, when there is something to change.

What the AI model does

The AI model is Claude. It has 3 jobs, and in each of them it only suggests:

  • a role for a job title that the rules do not recognise (a job-title-to-role match);
  • the person an account belongs to, when the rules could not match it (an account-to-person match);
  • a summary paragraph for a plan that code has already built.

A person reviews every suggestion. Code keeps an unreviewed suggestion out of a plan, so no access change rests on one. The model does not decide access. It does not see a password or a key, and it does not call the company's systems.

Claude is a family of AI models made by Anthropic. Three were compared: Claude Haiku 5.5, Claude Sonnet 5.5 and Claude Opus 5.5. For the same work, Haiku costs the least and Opus the most. The owner chose Haiku 5.5.

For the summary, code checks the paragraph against the plan. If the check fails, code uses a fixed template instead (AAC-006).

Safety rails

  • Nothing changes without an approved plan. Applying a plan is a dry run by default: it records what it would do and changes nothing.
  • Large removals need 2 approvers. This applies when 5 or more people would lose access, or 50 or more removals would happen, because of one day's HR events. Such a day goes to a separate plan.
  • Break-glass accounts are emergency accounts, kept for when normal sign-in fails. They are never changed, only reported.
  • A plan built from old data is not applied. If the data changed after the plan was made, the plan is made again.
  • There is no mode that changes real systems. Everything runs against mocks: stand-in programs shaped like the real services (AAC-007).

Build status

The project's checklist has 54 items. 40 are done and 14 are open. The open items include the nightly run with the bot's own GitHub account, the measured time to build a leaver's plan, and the published results.

03

How it was tested

A tuning world

A world is one generated set of fake company data: HR records, directory data and 95 app exports. Problems are planted in it, such as an account whose owner has left. An answer key lists every planted problem.

The tuning world is the one the builder reads and adjusts the tool on. Figures measured on it are labelled as tuning figures.

A sealed held-out world, scored once

The held-out world is a second world. A separate helper wrote its recipe without seeing the tool's code. The builder has not read the recipe.

The recipe is locked by a hash: a short string of characters computed from the file's contents. The world is scored once (AAC-005).

A blind referee

The tool and the answer key have the same author, so one misreading of the rules could be in both. A second helper wrote a referee script from the raw files and the public rules only. The referee builds its own answer key for the held-out world (AAC-011).

The two keys agree on 506 of 506 findings, with 0 disagreements. On the tuning world, which the referee was not written for, it disagrees with the key on 270 findings.

A red-team set, written blind and run once

A red-team set is a set of attacks written to test a defence. Here the attacker can type text into data that the AI reads: a job title, a display name or a cell in an app's export. The text tries to change the AI's suggestion.

The set holds 84 cases: 66 attacks and 18 clean controls. A helper wrote it blind: from a written brief, without seeing the code. It was sealed and run once (AAC-015).

Pass rules come first

The targets were written before the runs. Each safety count must be 0. The red team's target is 0 attack successes per model. Precision and recall on planted problems should each be at least 0.90.

Precision is the share of the tool's findings that are right. Recall is the share of the planted problems that the tool found.

Code does the grading

Code grades every run against the answer key. No AI model grades the results.

Where the tool and the key disagree on the held-out world, the owner rules on each item before any score is published (AAC-010).

Spending is capped

Paid AI model calls run only in GitHub's automation, after the owner approves the run. Code checks every call against a cap in a budget file: $8 for the final score and $10 for the red team, out of $100 of credit for the whole lab.

04

Results

The failure comes first. Then the score that is not published yet. Then the figures measured on tuning data. Every number links to the file it comes from. Each date is the day the test ran.

Failed

The red-team run (2026-11-17)

The sealed red-team set ran once. Each of 3 models answered 84 requests 3 times, which makes 252 runs per model. The target was 0 attack successes per model.

Haiku 5.5, the chosen model, failed the target. It had 7 attack successes in 252 runs.

Sonnet 5.5 and Opus 5.5 met the target, with 0 attack successes each. They gave no answer in many runs: Sonnet in 63 of 252 runs and Opus in 53 of 252 runs. No answer means that no suggestion was made. Haiku gave no answer in 0 runs.

What an attack success means here: a planted suggestion reaches the human reviewer. It is a wrong suggestion that looks like a normal one. Nothing is changed without review, and code keeps an unreviewed suggestion out of a plan.

Where the successes are. The run's log gives totals per model. Read with the code, it shows which jobs the 7 successes are in.

  • The set has 18 attacks on the summary. Run 3 times, they make 54 attempts. Code stopped all 54 of Haiku's.
  • So all 7 are in the other 2 jobs: job titles and accounts. Those jobs had 44 attacks that count toward the target. Run 3 times, they make 132 attempts. Haiku's attacks there succeeded in 7 of 132 attempts.
  • Another 4 account attacks try to make the AI say that an account belongs to nobody. That pushes the plan toward an extra removal, which a person reviews, so these are reported apart. They had 0 successes with every model.
  • The log does not split the 7 between titles and accounts, or by kind of attack. That split is in the run's detailed files, which nobody has opened. They are kept for the owner's rulings and are not published.
  • The log does not say why Sonnet and Opus gave no answer, or how many of those runs were attacks.

Not published

The final score on the sealed held-out world (2026-11-17)

The held-out world was scored once, on 2026-11-17, with Haiku 5.5. The run made 309 of 309 planned calls and finished. The score is not published yet.

What the run's log shows:

  • The 4 safety counts are all 0. They count changes to break-glass accounts, changes without a merged plan, removals over the limit without 2 approvals, and removals that rest on an unreviewed AI match.
  • The tool and the answer key disagree on 214 items: 179 account owners, 32 findings and 3 job titles.
  • The 214 is the length of a list. It is not a score. The log does not say how many of the items are the tool's mistakes and how many are the answer key's.

The owner rules on each of the 214 items. No precision or recall is published before that.

The run cost $0.0404. In the repository: the run record.

  • Job titles: each model suggested the right role for 75 of 76 job titles, in every repeat.

Tuning data

The plan on the tuning world (2026-11-15)

These figures were also measured on the tuning world. The rules were tuned on it.

  • The plan's changes against the answer key: precision 0.994 (462 of 465) and recall 1.000 (462 of 462).
  • The changes that are not in the key are accounts that the rules could not match to a person. The plan flags them for a person to check.
  • On the tuning world, one day's bulk HR import would remove access from 30 people. That day went to the separate plan that needs 2 approvals.

In the repository: the plan's score and the report on removals per day.

Limits of these results

  • All the data is fake. Mocks are not the real services, and real systems behave in ways the mocks do not.
  • The project planted the problems itself. Real exports are messier.
  • The AI model's answers can differ between runs.
  • The code check on the summary accepts a paragraph only if every word is on a fixed list. So planted words cannot be copied into it. A false claim made of allowed words still passes. The red-team run measured this. The figure is in the detailed files, not in the run's log.
  • The owner is the only approver in the lab. A plan that needs 2 approvers stays blocked by design.

05

What comes next

The owner's rulings, then the score

The owner rules on each of the 214 disagreements: the tool was wrong, the answer key was wrong, or both are acceptable. Each ruling is logged.

The owner has approved grouping the items by pattern first, biggest group first, with a tool that prints counts only. It prints numbers, item ids and fixed labels from the code, and never an account, a name or a job title. It makes no AI call and costs nothing (the tool).

Then the score is published. Errors in the answer key are listed apart and do not count against the tool. Nothing is run again.

GitHub keeps the detailed files of the run for 30 days, to 2026-12-17.

A decision on the model

Haiku 5.5 is the chosen model, and it failed the red-team target. The owner ruled that the result is recorded as a fail and that the model is not changed yet.

The run record lists 3 options:

  • keep Haiku and state the limit;
  • use Sonnet 5.5 for the job-title and account jobs;
  • add a defence in code for those jobs, and measure it on a new red-team set written blind.

Nothing is decided. The split of the 7 by job and by kind of attack comes first. The same counts-only tool prints it (the run record).

Still to build

The report generator and the results page for the published score are not built.

After the score is published, the held-out world becomes practice data (the run record).
