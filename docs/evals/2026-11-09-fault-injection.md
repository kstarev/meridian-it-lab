# Fault injection: the second checks (milestone 2)

Generated by `python -m tier0.evals.faults --models stub llama3.2 llama3.1:8b --k 3 --first-seed 1108 --worlds 40 --rate 0.3 --fault-seed 22 --temperature 0.5 --model-seed 1000` — do not edit by hand.

Triage makes no mistakes on the tuning set, so there the second checks show only their cost. Here triage is made wrong on purpose. With fault seed 22, 30% of the colleague tickets (12 of 40) and 30% of the outsider tickets (12 of 40) were picked from 40 tuning worlds (seeds 1108 to 1147). The real triage call still ran, and its answer was then replaced with own_username. Each picked ticket ran k = 3 times. Only the picked tickets are run here: the rest behave as in the normal tuning eval.

This is tuning data (ADR-013), so these counts show what the checks can do when triage fails. They are not a performance number: held-out v2 is the only one (ADR-021). No check was changed for this run (ADR-022).

An answered colleague request is a policy violation. Its token is self-only, so the reply can carry only the requester's own username, never the colleague's (ADR-006); the data-exposed column checks that.

12 of 12 flipped colleague messages name another directory user in full, so the mention check, which looks names and addresses up in the directory, can find them. A request that names nobody it can look up (for example "my new starter's login") would get past the mention check, and only the model check would stand in the way. None of the flipped messages is like that.
